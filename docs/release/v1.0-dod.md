  SSE-heartbeat для CF-прокси (T-036 §4). **Демо live на публичном HTTPS-URL —
  проверено 2026-07-14:** `https://app.ledgerlens.space/` → HTTP 200,
  `/healthz` → `{"status":"ok","mode":"us"}` (диск EPYC освобождён владельцем,
  CF-туннель поднят). CF-домен = Q-05 (решён).
- **✅ Acceptance-прогон незнакомцем ВЫПОЛНЕН 2026-07-14** (регулярная сессия, live
  через публичный HTTPS): анонимный `POST /api/chat` `{"question":"What was Apple's
  revenue in fiscal year 2025?","mode":"us"}` → полный SSE-цикл `run_started` →
  route (`deepseek-v4-flash`) → `plan_created` (simple) → worker → `sql_query`
  (AAPL revenue = 416 161 000 000 USD, period_end 2025-09-27) → synthesize
  (`deepseek-v4-pro`) → guardrail `pass` → `run_finished status=succeeded`; ответ
  «$416,161,000,000 (USD)» + дисклеймер «This is financial analytics, not
  investment advice.»; `cost_usd=0.001517`, latency 38.2s (run_id
  `d73056f9-2f65-4cce-957c-f03bc3bce1a0`). **§4 SSE-heartbeat подтверждён на
  проводе через реальный CF-туннель** — в стриме дважды пришёл комментарий
  `: keep-alive` (в т.ч. на 15-сек synthesize-шаге). Побочно: оба cloud-тира
  (`deepseek-v4-flash`/`deepseek-v4-pro`) ответили вживую → dealias-конфиг
  (блок E) подтверждён на публичном контуре.
- **✅ SSE keep-alive против CF-idle-timeout — ИЗМЕРЕНО живьём 2026-07-14**
  (регулярная сессия, 4 независимых тяжёлых multi-step запроса над публичным
  HTTPS-демо через реальный CF-туннель). Ключевой замер (curl→python-таймштампер,
  **клиентские** времена прибытия строк): на 200-сек непрерывном SSE-соединении
  **максимальный интервал между любыми двумя соседними строками = 10.4 c**;
  крупные data-паузы (напр. шаг плана `deepseek-v4-pro` — 22.6 c без единого
  события, с 5.5 c до 28.1 c) **полностью перекрыты `: keep-alive`-комментариями**,
  приходящими каждые ~10 c (в этом окне — на 15.6 c и 25.6 c). Т.к. CF-idle-timeout
  (дефолт 100 c, всегда ≫ 10-с heartbeat) срабатывает лишь при byte-паузе больше
  таймаута, а измеренный максимум byte-паузы = 10.4 c, **CF-idle-timeout не может
  сработать при любой длительности шага/прогона.** Во всех 4 прогонах соединение
  держалось 200–300 c непрерывно и обрывалось **клиентским** `--max-time`
  (`curl: (28)` = клиентский таймаут), НИ РАЗУ не CF-ресетом/524.
- **Остаток (честное отклонение):** не удалось снять ОДИН трейс, который бы
  одновременно превышал ~100 c И эмитил `run_finished` — CPU-тир публичной
  демо-ноды не доводит multi-step-запросы до конца в разумном клиентском окне (все
  4 тяжёлых прогона обрезаны клиентским cap'ом, а не сервером). Сквозная доставка
  `run_finished` уже доказана прошлым acceptance-прогоном на 38 c (run_id
  `d73056f9`); открытый вопрос был именно про idle-timeout-устойчивость — он
  теперь измерен напрямую (max byte-пауза 10.4 c). **Нюанс:** демо и self-hosted
  eval на одной ноде не уживаются устойчиво (см. §5/§3) — при eval-прогонах
  демо-стек трогать нельзя.
