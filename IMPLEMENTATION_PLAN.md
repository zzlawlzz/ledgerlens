# План реализации

**Проект:** Self-hostable мультиагентная платформа финансового анализа
**Аудитория документа:** агент-солюшен-архитектор, координирующий реализацию
**Парный документ:** ARCHITECTURE.md (что строим; здесь — как и в каком порядке)
**Бюджет времени:** 2 недели до MVP + 2 недели до прод-качества
**Декомпозиция:** выполнена — BACKLOG.md (задачи T-001…T-040 по приоритету, фазы → гейты G1–G4); конкретные контракты — CONTRACTS.md; вопросы владельцу — OWNER_QUESTIONS.md

---

## 0. Как пользоваться этим планом

Роль солюшен-архитектора: удерживать хребет, принимать/фиксировать архитектурные решения (§3), нарезать работу для агентов-разработчиков по фазам (§2), проверять фазы по критериям приёмки, не давать проекту расползтись.

**Главный риск проекта — не «чего-то не хватит», а «всё наполовину и хрупко».** Полусломанный широкий комплекс производит худшее впечатление, чем узкое железно работающее ядро. Отсюда все принципы ниже.

---

## 1. Руководящие принципы

1. **Хребет прежде уровней.** Сначала один сквозной путь работает end-to-end, потом навешиваются уровни. Каждый уровень самодостаточен и не ломает хребет.
2. **Вертикальный срез первым.** Неделя 1 — тонкий, но полный путь «вопрос → ответ на реальных данных», а не красиво сделанный один слой.
3. **Pluggable с первого дня.** Интерфейс адаптера источников закладывается в неделю 1, чтобы второй источник встал без переписывания. Но **реализуется сначала один** источник (US/EDGAR) — второй позже.
4. **Маркеры глубины важнее числа фич.** «Не пет-проект» делают eval в CI, распределённость, наблюдаемость, MCP — а не количество экранов. Эти маркеры доменно-независимы.
5. **Не размазывать.** Две ноды, не пять стран. Одна основная векторная БД, не все четыре. Один источник довести до конца прежде, чем начинать второй.
6. **Честность вместо натяжек.** vLLM не выдавать за полноценный CPU-режим — демонстрировать на GPU-ноде как бенчмарк. Локальная модель — для дешёвых шагов, тяжёлое в API.
7. **Резать с хвоста.** При нехватке времени режется хвост недели 4, а не хребет.

## 2. Фазовый план

### Фаза 1 — Вертикальный срез (Неделя 1)

**Цель:** напечатал вопрос → получил осмысленный ответ на реальных данных EDGAR. Некрасиво, но end-to-end.

**Скоуп:**
- Интерфейс `DataSourceAdapter` (§3.6 ARCHITECTURE) + **реализация только EDGAR**.
- Ingestion небольшого набора компаний (структурированные факты + несколько нарративных разделов) в Postgres.
- Один worker-агент (LangGraph, **ReAct**) с одним инструментом `sql_query`.
- Схема БД (§4 ARCHITECTURE), минимально достаточная.
- Голый чат-эндпоинт: вопрос → план → SQL → ответ.
- Всё в Docker, поднимается локально.

**Критерии приёмки:**
- `docker compose up` поднимает БД + агент + эндпоинт.
- Реальный вопрос по загруженным компаниям возвращает корректный ответ на основе фактических данных.
- Виден трейс шагов ReAct (в логах достаточно).
- Адаптерный интерфейс отделён от реализации EDGAR (второй источник теоретически встаёт за него).

**Зависимости:** решения ADR-1, ADR-4, ADR-5 (§3) должны быть приняты до конца фазы.

---

### Фаза 2 — MVP (Неделя 2)

**Цель:** работающий продукт, который не стыдно показать.

**Скоуп:**
- **Оркестратор** (LangGraph, **Plan-and-Execute**) поверх воркеров; воркеры вызываются через A2A-интерфейс (пока можно локально, без второй ноды).
- **RAG-инструмент** `rag_search`: retrieval по нарративным разделам с цитатами; основная векторная БД поднята; hybrid search + reranking (базово).
- **Model Router**: локальная CPU-модель (дешёвые шаги) + API (тяжёлое) с fallback.
- Минимальный **web-фронт** с живым стримом шагов агента (AG-UI).
- Non-advice guardrail на итоговом ответе.

**Критерии приёмки:**
- Многошаговый вопрос (сравнение + нарратив) обрабатывается: план → несколько шагов → синтез с цитатами.
- Виден стрим шагов в UI.
- Роутер реально разводит вызовы (лог показывает, что дешёвое ушло локально, тяжёлое — в API).
- Ответ с инвестиционной рекомендацией переформулируется/блокируется guardrail'ом.
- Демонстрируется дифференциатор: минимум один сценарий, где агент ловит противоречие/ошибку и переделывает шаг.

**Здесь заканчивается MVP-часть (2 недели).**

---

### Фаза 3 — Маркеры глубины (Неделя 3)

**Цель:** превратить MVP в «не пет-проект» — сигналы сениорности.

**Скоуп:**
- **Eval-слой:** golden dataset вопросов; прогон RAGAS + DeepEval + LLM-as-a-Judge; интеграция в **CI**; публикация результатов на дашборд.
- **Вторая нода:** один worker переезжает на VPS, связь по **A2A** — доказательство распределённости.
- **MCP:** инструменты оформляются как полноценные MCP-серверы (если в фазе 1–2 были упрощённо).
- **Второй источник (RU)** — если позволяет время: реализация RU-адаптера (MOEX ISS как минимум) за существующим интерфейсом. Иначе — переносится в буфер.

**Критерии приёмки:**
- CI-прогон гоняет eval и падает/сигналит при регрессии качества.
- На дашборде видны eval-скоры.
- Запрос реально обслуживается с участием воркера на удалённой ноде через A2A.
- Инструменты доступны как MCP-серверы.

---

### Фаза 4 — Полировка и упаковка (Неделя 4)

**Цель:** упаковать так, чтобы работодатель по ссылке всё понял за минуту.

**Скоуп:**
- **Слой B (мониторинг)** на n8n: US — новые 8-K; (RU — существенные факты, если RU-адаптер готов) → сводка → алерт.
- **Наблюдаемость** в Grafana: латентность, стоимость, eval-скоры, трейсы.
- **Фронт** причёсан (AG-UI), демо-режим играбелен незнакомцем без своих данных.
- **README** + **сайт-презентация** проекта (ссылка для сопроводительного письма).
- Финальная проверка: `docker compose up` разворачивает всё; бенчмарки (vLLM vs CPU vs API; Qdrant vs pgvector) оформлены в `benchmarks/`.

**Критерии приёмки:**
- Чистый клон → `docker compose up` → рабочая система (проверено на чистой машине).
- README объясняет архитектуру, стек, как запустить, что демонстрирует.
- Сайт-презентация отправляема ссылкой.
- Демо играбелен публично (US-режим на публичных данных EDGAR).

**Буфер/срез:** при нехватке времени первым режется слой B и часть наблюдаемости, затем RU-адаптер. Хребет (фазы 1–2) и маркеры глубины (eval, вторая нода) — не режутся.

## 3. Архитектурные решения к фиксации (ADR)

Принять в начале, до глубокой реализации. `[OPEN]` = требует актуальной проверки (данные после Jan-2026 могли измениться — не полагаться на память, проверить поиском на момент реализации).

| ID | Решение | Статус / примечание |
|---|---|---|
| ADR-1 | Схема нормализованной модели фактов (§4 ARCHITECTURE) | Зафиксировать базовый словарь метрик; РСБУ↔GAAP-маппинг итеративно |
| ADR-2 | Основная векторная БД: **Qdrant**; pgvector — связка + бенчмарк | Зафиксировано; одна основная, не набор |
| ADR-3 | Локальная CPU-модель | `[OPEN]` бенчмарк на актуальных моделях; предпочесть MoE-квантизацию. Железо зафиксировано (Q-06): 2×EPYC 7551, 128 ГБ RAM → кандидаты MoE-класса до ~30B |
| ADR-4 | Первый источник — **EDGAR (US)**; RU — второй | Зафиксировано |
| ADR-5 | Стратегии: оркестратор = Plan-and-Execute, воркеры = ReAct | Зафиксировано |
| ADR-6 | Embedding-модель (единая для док/запросов) | `[OPEN]` выбрать; учесть язык (RU-режим — многоязычность) |
| ADR-7 | Провайдеры cloud API и их роли в роутинге | **Решено (Q-01):** DeepSeek — cheap=deepseek-chat, strong/judge=deepseek-reasoner; облачного fallback нет (резерв — локальная модель); модели/цены пинуются в T-002 |
| ADR-8 | Провайдер цен (US, опционально) и его free-tier | **Решено (Q-10):** слой цен в скоупе этапа 3 (T-033); провайдер и free-tier проверяются в T-002; только end-of-day + кэш |
| ADR-9 | Канал алертов слоя B | **Решено (Q-03):** Telegram |
| ADR-10 | Границы demo-режима (публичные данные, без пользовательских) | Зафиксировано: US/EDGAR для публичного демо |

## 4. Сквозные воркстримы (идут через все фазы)

- **Адаптерный слой:** интерфейс — фаза 1; EDGAR — фаза 1; RU — фаза 3/буфер. Нормализация метрик расширяется по мере надобности.
- **Eval-харнесс:** мини-набор golden-вопросов полезно завести уже в фазе 2 (даже вручную), полноценный CI — фаза 3.
- **Наблюдаемость:** инструментировать вызовы (токены/стоимость/латентность) с фазы 2, дашборды — фаза 4.
- **Guardrails / non-advice:** ввести в фазе 2, покрыть eval-кейсами в фазе 3.

## 5. Риски и митигации

| Риск | Митигация |
|---|---|
| Расползание скоупа, всё наполовину | Жёсткий приоритет хребта; резать с хвоста (§1.7); фазовые критерии приёмки |
| CPU-инференс медленный/слабый | Tiered-роутинг: локально только дешёвое; тяжёлое в API; честный бенчмарк вместо натяжки |
| Дифференциатор «утонул» в text-to-SQL | Явно спроектировать и продемонстрировать сценарий самокоррекции агента (критерий приёмки фазы 2) |
| RU-источники: ограничения доступа/блокировки IP | RU-ingest на ноду с чистым доступом; устойчивость адаптера к недоступности; RU в буфере, не на критическом пути |
| Пейволл цен (US) | Цены — опциональный слой, end-of-day + кэш; не опора |
| Устаревшие сведения о моделях/ценах/API | ADR с пометкой `[OPEN]` проверяются поиском на момент реализации |
| Лицензия MOEX ISS (только ознакомление) | Демо/портфолио-использование; явное упоминание в README |
| EDGAR/cloud-API недоступны с RU IP (основная нода — в РФ) | Проверка доступности в T-002; egress-прокси `EDGAR_PROXY_URL` через VPS-FI (T-008); кэширование ingest |
| Хрупкость демо для незнакомца | Публичный demo-режим на US/EDGAR, играбелен без пользовательских данных |

## 6. Критический путь

```
Схема БД + адаптер-интерфейс + EDGAR ingest   (Ф1)
        └─> ReAct-воркер + sql_tool + чат      (Ф1)
                └─> оркестратор P&E + RAG + роутер + UI-стрим   (Ф2)  ← MVP
                        └─> eval в CI + вторая нода A2A + MCP    (Ф3)
                                └─> слой B + Grafana + сайт + упаковка  (Ф4)
```

Всё, что не на этой линии (RU-адаптер, бенчмарки, часть наблюдаемости), — параллельно/в буфер, не блокирует хребет.

## 7. Definition of Done (портфолио-готовность)

- [ ] `docker compose up` на чистой машине → рабочая система.
- [ ] Публичный demo-режим (US/EDGAR) играбелен незнакомцем по ссылке.
- [ ] Многошаговый агентский анализ с видимым планом, шагами и минимум одним сценарием самокоррекции.
- [ ] RAG с цитатами на первоисточник; guardrail против инвестрекомендаций.
- [ ] Eval в CI + eval-скоры на дашборде.
- [ ] Распределённость: воркер на удалённой ноде через A2A.
- [ ] Инструменты как MCP-серверы; стрим в UI через AG-UI.
- [ ] Наблюдаемость в Grafana (латентность, стоимость, качество).
- [ ] Бенчмарки оформлены (локальные CPU-модели vs API — vLLM-GPU исключён решением владельца Q-07, отсутствие честно объяснено в отчёте; Qdrant vs pgvector).
- [ ] README + сайт-презентация; лицензии источников упомянуты.
- [ ] Pluggable-архитектура: второй источник встаёт за интерфейс (RU реализован или явно оставлен как расширение с готовым интерфейсом).
