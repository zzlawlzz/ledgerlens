# Архитектурная документация

**Проект:** Self-hostable мультиагентная платформа финансового анализа
**Аудитория документа:** агенты-разработчики (Claude Code / Cursor / Codex), реализующие компоненты системы
**Статус:** зафиксированные архитектурные решения. Всё, что помечено `[OPEN]`, требует отдельного решения (см. IMPLEMENTATION_PLAN.md)
**Связанные документы:** CONTRACTS.md (конкретные контракты: DDL, схемы инструментов, конвенции) · BACKLOG.md (декомпозиция работ T-001…T-040) · OWNER_QUESTIONS.md (вопросы владельцу)

## 1. Назначение и границы

### 1.1. Что это

Самостоятельно разворачиваемая мультиагентная система, которая отвечает на аналитические вопросы по финансовым данным публичных компаний. Пользователь задаёт вопрос на естественном языке → система строит многошаговый план анализа → агенты обращаются к структурированным данным (SQL) и к нарративным разделам отчётности (RAG) → возвращают ответ с числами, динамикой и ссылками на источник, стримя ход рассуждения в интерфейс.

Поверх основного сценария работает **слой мониторинга (B)**: по расписанию отслеживаются новые события раскрытия (новые отчёты / существенные факты), формируются сводки и алерты.

### 1.2. Ключевой дифференциатор

Система — **не** text-to-SQL обёртка. Ценность в **агентности**: план из нескольких шагов, самопроверка, обнаружение и исправление собственной ошибки в запросе, подкрепление нарративных выводов цитатами из первоисточника. Реализация должна делать этот цикл наблюдаемым (видно план, шаги, инструменты, коррекции).

### 1.3. Позиционирование: аналитик, а не советник

Система предоставляет **факты, расчёты, сравнения и объяснения с опорой на отчётность**. Она **не** даёт инвестиционных рекомендаций («покупать / продавать / держать»), не прогнозирует цены и не советует распределение капитала.

Это архитектурное требование, а не косметика:
- В каждый системный промпт агента, формирующего итоговый ответ, включается ограничение на непредоставление инвестсоветов.
- В UI присутствует явный дисклеймер.
- Guardrail-проверка итогового ответа на формулировки-рекомендации (см. §11).

### 1.4. Goals / Non-goals

**Goals:** демонстрация production-подобной агентской архитектуры; воспроизводимое развёртывание одной командой; сменяемость источников данных (US / RU); измеримое качество (eval в CI); распределённость (несколько нод); наблюдаемость.

**Non-goals:** высокочастотные/real-time торговые данные; инвестиционные рекомендации; охват всех мировых рынков; масштабирование на тысячи одновременных пользователей; полнота покрытия всех форм отчётности.

## 2. Высокоуровневая архитектура

### 2.1. Слои

```
┌───────────────────────────────────────────────────────────┐
│  Presentation:  Web UI (React/TS) ← AG-UI stream            │
├───────────────────────────────────────────────────────────┤
│  Orchestration: Orchestrator-агент (LangGraph, Plan&Execute)│
│                       │  A2A                                 │
│                 Worker-агенты (ReAct)                        │
├───────────────────────────────────────────────────────────┤
│  Tools (MCP servers): SQL-tool · RAG-tool · Enrichment-tool │
├───────────────────────────────────────────────────────────┤
│  Model Router:  local CPU inference ⇄ cloud API (fallback)  │
├───────────────────────────────────────────────────────────┤
│  Data:  Postgres (+pgvector) · Qdrant · Source Adapters     │
│         Ingestion pipeline · Monitoring (n8n)               │
├───────────────────────────────────────────────────────────┤
│  Ops:  Docker · Grafana (observability) · Eval harness (CI) │
└───────────────────────────────────────────────────────────┘
```

### 2.2. Жизненный цикл запроса

1. UI отправляет вопрос → открывается AG-UI стрим.
2. **Orchestrator** классифицирует задачу и строит план (Plan-and-Execute): список подзадач (например: «получить выручку по компаниям X,Y за 3 года» → «сравнить динамику» → «поднять risk factors по X» → «синтез»).
3. Для каждой подзадачи оркестратор делегирует **Worker**-агенту (по A2A — локально или на удалённой ноде).
4. Worker работает в цикле **ReAct**: рассуждение → вызов инструмента (MCP) → наблюдение → повтор, пока подзадача не решена. Инструменты: SQL по фактам, RAG по нарративу, enrichment (цены).
5. Каждый вызов LLM проходит через **Model Router** (дешёвые шаги → локальная модель, тяжёлое рассуждение → API).
6. Промежуточные шаги стримятся в UI через AG-UI.
7. Оркестратор синтезирует финальный ответ, прогоняет guardrail (non-advice), возвращает с цитатами.
8. Трейс (шаги, токены, стоимость, латентность) пишется в слой наблюдаемости.

## 3. Компоненты

### 3.1. Orchestrator (LangGraph, Plan-and-Execute)

- Реализуется как граф состояний LangGraph.
- Стратегия **Plan-and-Execute**: сначала строит явный план, затем исполняет шаги, при необходимости — репланирование после неуспешных/противоречивых результатов.
- Держит состояние сессии: план, результаты шагов, историю, бюджет (лимиты токенов/стоимости/итераций).
- Делегирует подзадачи воркерам через A2A-клиент.
- **Не** вызывает инструменты напрямую — только через воркеров (чистое разделение планирования и исполнения).

### 3.2. Worker-агенты (ReAct)

- Каждый worker — ReAct-цикл: `thought → action(tool) → observation → …`.
- Получает подзадачу + контекст от оркестратора, возвращает результат + трейс шагов.
- Инструменты подключаются как MCP-клиенты (см. §6).
- Ограничения на число итераций и на бюджет во избежание зацикливания.
- Воркеры могут исполняться на разных нодах (см. §7).

### 3.3. Tool layer (MCP servers)

Каждый инструмент — отдельный MCP-сервер с декларативной схемой. Минимальный набор:

| Инструмент | Назначение | Вход | Выход |
|---|---|---|---|
| `sql_query` | Выполнение SQL по нормализованной модели фактов | SQL или структурированный запрос | таблица результатов + метаданные |
| `schema_introspect` | Описание доступных таблиц/метрик для агента | — | схема, словарь метрик |
| `rag_search` | Поиск по нарративным разделам отчётности | текст запроса, фильтры | чанки + источники для цитирования |
| `price_enrich` | End-of-day цены (опционально) | тикер, период | ряд цен (кэшируемый) |

Требования: строгая JSON-схема параметров; идемпотентность чтения; таймауты; понятные ошибки (агент должен уметь среагировать на ошибку и переформулировать).

### 3.4. Model Router (tiered inference)

Маршрутизирует вызовы LLM по стоимости/сложности:
- **Локальная модель** (CPU-инференс, см. §7.1) — дешёвые/простые вызовы: классификация, роутинг, короткие извлечения, форматирование.
- **Cloud API** (Claude / OpenAI / Gemini / DeepSeek) — тяжёлое рассуждение, планирование, финальный синтез.
- **Fallback**: при недоступности/таймауте локальной — деградация в API (и наоборот, где применимо).
- Провайдер-агностичный интерфейс: единый вызов, за которым скрыт конкретный backend.
- `[OPEN]` конкретная локальная модель — решается бенчмарком на актуальных данных (знания об оптимальной CPU-модели устаревают; MoE-модели на CPU дешевле за токен — учесть при выборе).

### 3.5. RAG-подсистема

Пайплайн: `ingest → chunk → embed → store → retrieve → (hybrid + rerank) → cite → generate`.

- **Chunking**: нарративные разделы отчётности режутся на чанки с перекрытием; параметры (размер/overlap) — настраиваемые, влияют на качество.
- **Embedding**: единая embedding-модель для документов и запросов.
- **Store**: основная векторная БД — **Qdrant** (self-host). **pgvector** в Postgres — как связка с реляционными данными и как объект бенчмарка «Qdrant vs pgvector» (сознательный выбор одного основного хранилища, а не набора всех).
- **Hybrid search**: векторный + полнотекстовый/ключевой поиск (точные термины, тикеры, названия статей отчётности).
- **Reranking**: переупорядочивание top-k перед подачей в LLM.
- **Citations**: каждый нарративный вывод сопровождается ссылкой на исходный документ/раздел. Anti-hallucination: агент отвечает «нет данных», если контекст не покрывает вопрос.

### 3.6. Data Source Adapters (pluggable)

Ядро сменяемости источников. За единым интерфейсом адаптера скрыт конкретный источник; режим выбирается конфигом.

- **US mode**: SEC EDGAR (+ опц. цены).
- **RU mode**: MOEX ISS + ГИР БО + e-disclosure.

Адаптер отвечает за: получение сырых данных источника, нормализацию в внутреннюю модель (§4), извлечение нарратива для RAG, определение потока событий для слоя мониторинга. См. §5 по спецификации источников.

Интерфейс адаптера (концептуально):
```
DataSourceAdapter:
    list_entities() -> [Company]
    fetch_filings(company, period_range) -> [Filing]
    extract_facts(filing) -> [FinancialFact]     # нормализация в единую модель
    extract_sections(filing) -> [FilingSection]  # нарратив для RAG
    poll_events(watchlist) -> [Event]            # для слоя B
```

### 3.7. Ingestion pipeline

- Загружает данные из источника через адаптер, нормализует, пишет в Postgres (факты) и Qdrant/pgvector (эмбеддинги нарратива).
- Кэширование: данные закрытого периода не меняются — кэшировать и не перезапрашивать.
- Соблюдение rate-limit источника (см. §5).
- Идемпотентность: повторный ingest не дублирует записи (ключ по источник+сущность+период+номер корректировки).

### 3.8. Monitoring / Alert layer (B) — n8n

- Лёгкий слой, **не** ядро.
- По расписанию опрашивает источник на новые события (US: новые 8-K; RU: существенные факты на e-disclosure).
- Новое событие → агент формирует сводку → алерт (канал уведомления `[OPEN]`).
- Реализуется на n8n (плановый ингест, ветвление, уведомления).

### 3.9. Evaluation subsystem

- **Golden dataset**: набор вопросов с эталонными ответами/ожиданиями.
- Прогоны: **RAGAS** (качество RAG), **DeepEval** (метрики), **LLM-as-a-Judge** (оценка ответов моделью-судьёй).
- Запускается в **CI**; результаты публикуются на дашборд.
- Метрики (примерно): релевантность контекста, faithfulness (нет галлюцинаций), корректность SQL-результата, наличие цитат, стоимость/латентность.

### 3.10. Observability — Grafana

- Трейсы шагов агентов, латентность, стоимость (токены×цена), eval-скоры.
- Источник метрик: слой инструментирования вызовов LLM/инструментов + результаты eval.
- Дашборды: по сессии, агрегированно, тренд качества по прогонам.

### 3.11. Persistence — Postgres / Supabase

Хранит: нормализованные финансовые факты, метаданные отчётов, нарративные разделы + эмбеддинги (pgvector), состояние/память сессий агентов, логи, результаты eval. Схема — §4.

## 4. Модель данных

Базовая реляционная модель (Postgres). Спроектирована так, чтобы в неё сводились и US-GAAP (EDGAR), и РСБУ (ГИР БО) через адаптеры.

```
companies
  id (pk)
  source            -- 'edgar' | 'moex' | 'girbo' | 'edisclosure'
  external_id       -- CIK (US) | ИНН/тикер (RU)
  ticker
  name
  sector
  meta (jsonb)

filings
  id (pk)
  company_id (fk -> companies)
  form_type         -- '10-K'|'10-Q'|'8-K' (US) | 'БФО'|'сущ.факт'|'эмитентский отчёт' (RU)
  period            -- отчётный период
  filed_at
  correction_number -- для идемпотентности (RU: номер корректировки)
  source_url

financial_facts
  id (pk)
  filing_id (fk -> filings)
  metric            -- каноническое имя метрики во внутреннем словаре
  value
  unit
  period
  standard          -- 'US-GAAP' | 'РСБУ'  (для трассируемости нормализации)

filing_sections
  id (pk)
  filing_id (fk -> filings)
  section           -- 'risk_factors'|'md&a'|... (US) | эквиваленты (RU)
  text
  embedding         -- pgvector (или ссылка в Qdrant)
```

**Нормализация метрик:** внутренний словарь канонических метрик (`revenue`, `net_income`, `total_assets`, …), в который адаптеры маппят строки US-GAAP и РСБУ. Поле `standard` сохраняет исходный стандарт для прозрачности. `[OPEN]` полный маппинг РСБУ↔GAAP — итеративная задача (начать с базового набора метрик).

## 5. Спецификация источников данных

### 5.1. US — SEC EDGAR (опора US-режима)

- Доступ **бесплатный, без API-ключа**; обязателен заголовок `User-Agent` с контактами.
- Rate-limit: пауза ~100 мс между запросами; для массовой загрузки — bulk-выгрузки вместо поштучных вызовов; кэшировать (закрытый период неизменен).
- Структурированные данные: XBRL-факты из 10-K / 10-Q → income statement, balance sheet, cash flow (US-GAAP).
- Нарратив для RAG: risk factors, MD&A из 10-K/10-Q.
- События для слоя B: **8-K** (существенные события), прилетают ежедневно.
- Base URL: `https://data.sec.gov/`.

### 5.2. US — цены (опционально, обогащение)

- **Не опора**, тонкий опциональный слой. Free-tier провайдеров жёстко лимитирован (порядок величины — десятки вызовов в день у части провайдеров), поэтому: только **end-of-day**, с кэшированием, без real-time поллинга.
- `[OPEN]` выбор провайдера и его актуальный free-tier — проверить на момент реализации (ландшафт быстро меняется; часть провайдеров без бесплатного тарифа).

### 5.3. RU — MOEX ISS (опора RU-режима, рыночные данные)

- `iss.moex.com`. Данные по рынкам Мосбиржи: инструменты, свечи, сделки, котировки, история. **Задержанные — бесплатно**, real-time — по подписке.
- REST, форматы XML/CSV/JSON. Есть зрелая Python-библиотека `apimoex`.
- **Лицензия:** данные ИСС предоставляются только для ознакомления, не для извлечения прибыли/перепродажи без договора с биржей. Для портфолио/демо — приемлемо; **обязательно** упомянуть лицензию в README.

### 5.4. RU — ГИР БО (фундаментал, РСБУ)

- `bo.nalog.gov.ru` (Ресурс БФО): бухотчётность российских организаций с 2019 (у части — с 2011).
- Базовая отчётность бесплатна; полный доступ с ежемесячной выгрузкой — платное абонентское обслуживание (порядка сотен тыс. руб./год).
- **Особенности (важно учесть):**
  - После 2022 (ПП РФ №395) компании могут ограничить/заблокировать доступ третьих лиц; частичное ограничение (пояснения + аудиторские заключения) применяется автоматически.
  - Компании под санкциями могут исключаться из ресурса (ПП №35/2020).
  - Данные — **РСБУ**, отчётность единичного юрлица (не консолидированная МСФО).
  - Официального чистого публичного REST API нет — серая зона; проектировать адаптер устойчиво к недоступности данных.

### 5.5. RU — e-disclosure.ru (нарратив + события)

- Центр раскрытия корпоративной информации (Интерфакс). По публичным эмитентам: ежеквартальные/годовые отчёты + **существенные факты**.
- Нарратив для RAG: разделы эмитентских отчётов (риски, разбор результатов).
- События для слоя B: существенные факты — прямой аналог 8-K.

### 5.6. Практическое ограничение размещения

Доступ к российским госресурсам (MOEX ISS, nalog) с зарубежных IP бывает нестабилен/блокируется в обе стороны. Ingest RU-источников вешать на ноду с чистым доступом к ним, а не на произвольную заграничную VPS. Заложить в топологию нод (§7).

**Зеркальный риск (актуален: основная нода — в РФ):** доступность `sec.gov`/`data.sec.gov` (и потенциально cloud-LLM API) с российских IP может быть ограничена. Митигация: EDGAR-клиент поддерживает опциональный egress-прокси `EDGAR_PROXY_URL` (поднимается на зарубежной VPS); фактическая доступность проверяется на старте реализации (задача T-002 бэклога).

## 6. Агентские протоколы

| Протокол | Где | Роль |
|---|---|---|
| **MCP** | Tool layer | Инструменты выставляются как MCP-серверы; воркеры — MCP-клиенты. Стандартизирует доступ к инструментам вместо хардкода функций. |
| **A2A** | Orchestrator ↔ Workers | Межагентное взаимодействие, в т.ч. между нодами. Доказательство распределённости. |
| **AG-UI** | Backend ↔ Web UI | Стриминг шагов агента в интерфейс в реальном времени. |

## 7. Топология развёртывания

### 7.1. Ноды

| Нода | Роль | Особенности |
|---|---|---|
| Домашний сервер (2×EPYC, **без GPU**) | Основная: оркестратор, БД, инструменты, локальный инференс | CPU-инференс квантованных моделей (GGUF через llama.cpp/Ollama, OpenAI-совместимый эндпоинт). MoE-модели на CPU дешевле за токен. |
| Удалённая VPS | Одна worker-нода через A2A | Доказательство распределённости. Двух нод достаточно — не размазывать по многим странам. |
| Арендованная GPU-нода | **Только для бенчмарка** vLLM | Разовый бенчмарк «vLLM-GPU vs llama.cpp-CPU vs API» по латентности/стоимости/качеству. vLLM на CPU не выдавать за полноценный режим. |
| Нода с чистым доступом к RU-ресурсам | Ingest RU-источников | См. §5.6. |

**Фактическая топология (зафиксирована решениями владельца, Q-05/Q-06/Q-07, 2026-07-10):**
- **Домашняя нода (РФ):** 2× EPYC 7551 (64C/128T), 128 ГБ RAM, белый IP — основной стек (оркестратор, БД, инструменты, локальный MoE-инференс) + RU-ingest (нода в РФ = чистый доступ к RU-ресурсам).
- **VPS-FI (Финляндия):** удалённая worker-нода (A2A, T-031) + опциональный egress-прокси для EDGAR (§5.6, зеркальный риск).
- **VPS-KZ (Казахстан):** резерв, в рабочую топологию не включается (принцип «не размазывать»).
- **Публичный вход демо:** Cloudflare Tunnel к домашней ноде (домен на CF DNS); IP не публикуется; фолбэк — прямой вход на белый IP.
- **GPU-нода:** исключена решением владельца (Q-07) — инференс-бенчмарк проводится без vLLM-GPU (локальные CPU-модели vs API).

### 7.2. Контейнеризация

- Каждый сервис — отдельный контейнер (Docker).
- Оркестрация локально — `docker compose`; цель: `docker compose up` разворачивает систему.
- Сервисы: orchestrator, workers, каждый MCP-сервер, локальный inference, Postgres, Qdrant, n8n, Grafana, web UI.

## 10. Сквозные требования

- **Секреты:** API-ключи — только через переменные окружения/секрет-менеджер, никогда в коде/репозитории. Агенты **не** обрабатывают учётные/платёжные данные.
- **Контроль стоимости:** бюджет на сессию (лимит токенов/стоимости/итераций); tiered-роутинг для дешёвых шагов; кэш результатов.
- **Обработка ошибок:** таймауты и ретраи на вызовах инструментов/моделей/источников; агент должен уметь среагировать на ошибку инструмента и переформулировать, а не падать.
- **Идемпотентность ingest:** ключ источник+сущность+период+номер корректировки.
- **Non-advice guardrail:** проверка итогового ответа на инвестиционные рекомендации; при срабатывании — переформулировка в аналитический вид.
- **Устойчивость к недоступности источника:** особенно RU (ограничения доступа, блокировки IP) — деградация без падения всей системы.

## 11. Глоссарий

- **Plan-and-Execute** — стратегия агента: сначала строится явный план, затем шаги исполняются (с возможным репланированием).
- **ReAct** — цикл агента: рассуждение → действие (инструмент) → наблюдение → повтор.
- **MCP** — протокол выставления инструментов агентам.
- **A2A** — протокол межагентного взаимодействия (в т.ч. между нодами).
- **AG-UI** — протокол стриминга шагов агента в интерфейс.
- **RAG** — генерация ответа с опорой на найденные фрагменты документов.
- **XBRL** — машиночитаемый формат финансовой отчётности (EDGAR).
- **РСБУ / US-GAAP** — российские / американские стандарты бухучёта.
- **Существенный факт** — раскрываемое публичным эмитентом РФ значимое событие (аналог 8-K).
- **ГИР БО / БФО** — государственный ресурс бухгалтерской (финансовой) отчётности РФ.
