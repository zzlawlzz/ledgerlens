**Решение:** ✅ 2026-07-11 — владелец добавил секрет (`gh secret set DEEPSEEK_API_KEY --repo zzlawlzz/ledgerlens`, PowerShell-вариант через `Get-Content .env | Select-String ...`, т.к. bash-редирект `<` не работает в PowerShell). `gh secret list` подтверждает наличие. `eval.yml` запущен повторно (run 29154312335) для живого подтверждения — результат смотреть в BACKLOG §1 сноске T-030.

## Q-18 · VPS-FI (T-031) — общий боевой сервер, а не чистая нода под воркер
**Контекст:** при подготовке к T-031 (вторая нода, гейт G3) проверил текущее состояние VPS-FI (31.58.137.203 — та же машина, что уже используется как EDGAR-прокси). Обнаружено: это не выделенный сервер под проект, а личный боевой сервер владельца с уже работающими сервисами — Amnezia VPN (xray+awg2), MTProto-прокси, и **процесс `/opt/trading-bot/run.py`, использующий ~300 МБ / 15% RAM** (похоже на реально торгующего бота). Ресурсы тесные: всего 1.9 ГБ RAM, свободно ~100 МБ; `docker compose` plugin не установлен (только голый `docker`). Деплой ещё одного контейнера (LangGraph-воркер + Caddy для TLS) в таких условиях рискует упереться в OOM и уронить существующие сервисы — в том числе, возможно, что-то денежное.
**Варианты:** (а) выделить для T-031 отдельную чистую VPS (новые расходы, но безопасно и соответствует духу «маркер распределённости» из ТЗ); (б) ставить лёгкий воркер-контейнер прямо на VPS-FI рядом с существующими сервисами, с явным `mem_limit` в compose и предварительной проверкой, что 100 МБ свободных хватит (рискованно при текущем запасе); (в) сначала разобраться, что ест память на VPS-FI, и освободить её (если там что-то некритичное).
**Рекомендация:** (а) — не трогать боевой сервер с торговым ботом ради демонстрационной задачи портфолио; отдельная минимальная VPS (1 vCPU/1-2 ГБ) стоит недорого и убирает риск.
**Дефолт:** T-031 не начата, ничего не задеплоено на VPS-FI. Агент не стал самостоятельно принимать решение о выделении новых денежных ресурсов (аренда VPS) или об изменении конфигурации боевого сервера — оба варианта требуют явного решения владельца.
**Решение:** ✅ 2026-07-11 — владелец выделил отдельный, практически неиспользуемый сервер под T-031: IP `104.238.24.196`, 1 vCPU, 957 МБ RAM (~600 МБ доступно с учётом reclaimable cache), 15 ГБ диска (7.9 ГБ свободно), Ubuntu 22.04, Docker 29.1.3 уже установлен (`docker compose` плагина нет — поставить в T-031). Из стороннего — только лёгкий `amneziawg-go` (~1.3% RAM), торгового бота или другой тяжёлой нагрузки нет. Доступ был передан паролем в чате (root) — агент немедленно завёл отдельный SSH-ключ (`~/.ssh/id_ed25519_worker_node`), установил его в `authorized_keys` и больше не использует и не хранит пароль нигде в репозитории; **владельцу стоит сменить root-пароль на этом сервере через панель хостера** (гигиена — пароль был один раз показан в чате открытым текстом). Ресурсов достаточно: воркер-контейнер на основном стенде сейчас потребляет ~170 МБ RAM (тяжёлые embedding/reranker-модели остаются на mcp-rag на домашней ноде, воркер обращается к ним по сети через MCP) — с Caddy и ОС должно уложиться в доступные ~600 МБ с запасом. T-031 разблокирована, можно начинать реализацию.

## Q-19 · EOD-провайдер цен для T-033: Stooq блокирует бот-детекцией
**Контекст:** T-033 (price_enrich) реализован полностью — кэш в таблице `prices`, rate-limit + суточный счётчик, MCP-сервер mcp-enrich, инструмент у воркера, честная деградация при недоступности провайдера, 14 юнит-тестов. Провайдер по умолчанию — Stooq EOD CSV (выбран в T-002 как «дефолт-кандидат, без ключа»). При живой проверке выяснилось: **stooq.com отдаёт эндпоинт `/q/d/l/` не-браузерным клиентам (curl/httpx) JS proof-of-work challenge (SHA-256), независимо от User-Agent.** Прямой браузерный GET работает (фикстура снята с браузерной страницы), но продакшн-httpx получает HTML-челлендж вместо CSV. Обходить бот-детекцию (решать PoW) — запрещённое действие, субагент корректно отказался. Следствие: live-критерий T-033 «ряд EOD-цен в ответе + повтор из кэша без внешнего вызова» не проходит с этой сети/этим клиентом; инструмент при этом честно возвращает retryable-ошибку и основной анализ не ломается (это как раз работает).
**Варианты:** (а) гнать Stooq через egress-прокси/браузерный рендер — сомнительно (челлендж клиентский, прокси его не решит; понадобился бы headless-браузер, тяжело); (б) сменить EOD-провайдера на дружественный к серверным клиентам без ключа или с бесплатным ключом — кандидаты: **Alpha Vantage** (бесплатный ключ, лимит 25 запросов/день — тесно, но для демо-кэша хватает; уже упоминался в T-002 как альтернатива ADR-8), Financial Modeling Prep, Tiingo, Twelve Data (у всех free-tier с ключом), либо Yahoo Finance неофициально (нестабильно); (в) для US-цен взять готовый источник, который у нас УЖЕ есть — по факту цены нужны как «контекст динамики», а EDGAR даёт фундаментал; можно ограничить T-033 демонстрацией на кэшированных данных (записать один раз с браузера в `prices`, инструмент работает из кэша) и пометить live-провайдер как «требует ключа/сети без челленджа» — минимально, но закрывает архитектуру; (г) признать, что цены — самый низкоприоритетный слой (Q-10: «режется первым при срыве сроков»), и оставить T-033 в wip до решения по провайдеру.
**Рекомендация:** (б) с Alpha Vantage — бесплатный ключ, серверный доступ, тот же паттерн, что EDGAR (ключ в .env); лимит 25/день не проблема при кэше в `prices`. Нужен только бесплатный API-ключ владельца (регистрация на alphavantage.co, минута). Если владелец против ещё одного ключа — вариант (в): демонстрация из кэша.
**Дефолт (применён без ожидания):** T-033 остаётся `[wip]`; код полностью готов и абстрагирован от провайдера (сменить = один класс-провайдер + ключ). Агент не регистрирует сторонние аккаунты/ключи самостоятельно. Жду решения владельца по провайдеру.
